# ADR-0008: 离线融合架构采纳方案 B（构建期稳定原局预计算 + 运行时流年月交互）

## 状态
**ACCEPTED**（2026-10-09）

## 背景
将复杂的命理推演（大运十步周期、起运岁数、原局 22 类关系、喜用格局）接入 Android APP 时，存在两种架构方案：
1. **方案 A（Kotlin 全量运行时计算）**：将天文节气、lunar-python 排运逻辑全部移植进 Kotlin。
   - 缺陷：需要自带 1990–2035 年分钟级节气表（1100+ 条），移植起运 `sect=1`、时辰粒度等隐式行为极易产生微小偏差，对拍难度极大。
2. **方案 B（构建期预计算 + 运行时轻量交互）**：
   - 随股票上市日确定的稳定命理事实（大运方向、起运日、12 个大运区间、2776 唯一上市盘的原局内部关系、喜用候选）在 Python 构建期离线生成并固化入 SQLite。
   - 运行时仅由 Kotlin 执行流年、流月与原局的 22 类关系事件匹配与文案组合。

## 决策
1. **全面采纳方案 B**。该方案与 V1.2 的构建设计（四柱、藏干、强弱构建期生成，运行时读库）完全同构。
2. **唯一盘去重**：全库 5395 只股票对应 2776 张唯一上市盘（`listing_date` 唯一）。原局关系和喜用分析按 2776 张唯一盘构建并映射，大幅节约数据库体积（预估仅增加约 4–5 MiB，远低于 16MB 预置库与 25MB APK 上限）。
3. **数据库无缝迁移**：更新 `SCHEMA_VERSION=2`，利用 `AppDatabase` 已有机制（自动备份收藏 $\rightarrow$ 重新复制预置库 $\rightarrow$ 还原收藏），免去编写复杂 Room migration 脚本。
4. **纯离线运行**：严禁运行时通过网络或后台进程调用外部服务。

## 后果
- 保证构建产物 100% 可复现、可离线验证与跨仓对拍。
- 保证 Android 客户端运行时极速响应（仅简单索引查询与规则过滤），无复杂天文历算性能开销。
